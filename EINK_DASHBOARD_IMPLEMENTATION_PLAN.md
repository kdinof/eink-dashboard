# E-Ink Dashboard для Meebook — план реализации

Дата подготовки: 16 июля 2026  
Статус: технический план перед началом разработки

Исполнение отдельными агентами описано в [`AGENT_EXECUTION_PLAN.md`](AGENT_EXECUTION_PLAN.md). Этот файл остаётся источником продуктовых и технических требований; агентский план задаёт зависимости, границы задач, отчёты и порядок передачи работы.

## 1. Цель проекта

Создать надёжное нативное Android-приложение для e-ink-читалки Meebook с Android 11. Приложение должно работать как постоянно открытый персональный информационный дашборд и показывать:

- часы и дату;
- уровень заряда устройства;
- события Google Calendar;
- задачи Todoist;
- текущую погоду и прогноз;
- состояние последнего обновления и офлайн-режим.

Приложение должно быть рассчитано на e-ink-экран, поддерживать портретную и альбомную ориентации, минимизировать ghosting и сохранять последние полученные данные при отсутствии сети.

Проект изначально делается только для одного пользователя, но архитектура должна позволять добавлять новые информационные блоки.

## 2. Исходное устройство

Известные данные:

- производитель: Meebook;
- пользователь указал модель M103;
- Android 11;
- обычные APK можно устанавливать;
- Google Play Services присутствуют;
- пользователь готов включить режим разработчика и USB debugging;
- разрешение, DPI, ABI и точные e-ink API необходимо определить через ADB.

Важно: в первоначальном описании упоминался Meebook M8, а затем M103. Перед началом разработки необходимо подтвердить точную модель командой ADB и не полагаться на название из переписки.

## 3. Зафиксированные продуктовые требования

### Режим работы

- обычное полноэкранное приложение;
- отдельный `Dashboard mode`;
- преимущественно статичный экран;
- данные обновляются только пока приложение открыто;
- кнопка питания штатно выключает и включает экран;
- после пробуждения приложение остаётся открытым и немедленно обновляет данные;
- опциональная настройка «Не выключать экран»;
- обновление отображаемого времени каждую минуту;
- поддержка портретной и альбомной ориентаций;
- чёрно-белая палитра и оттенки серого;
- обязательная оптимизация под e-ink и борьба с ghosting.

### Google Calendar

- календарь только для просмотра;
- режимы:
  - сегодня;
  - сегодня и завтра;
  - неделя;
- пользователь может выбирать режим;
- поддержка нескольких календарей;
- календари должны визуально различаться;
- описание, участники и ссылки на звонки не обязательны.

### Todoist

- представления «Сегодня» и «Предстоящие»;
- отображение приоритета, проекта, срока, labels и подзадач;
- просмотр задач;
- завершение задач с устройства;
- создание и редактирование задач не требуются.

### Погода

- Ташкент как место по умолчанию;
- возможность использовать текущее местоположение;
- текущая погода;
- прогноз на день;
- прогноз на неделю.

### Хранение и сервер

- предпочтительно всё выполнять непосредственно на устройстве;
- приложение должно показывать последние доступные данные офлайн;
- Cloudflare допустим, но для первой версии не нужен;
- публикация для других пользователей пока не планируется.

## 4. Решение по формату приложения

### Основной вариант

Реализовать обычное нативное Android-приложение с одной полноэкранной Activity и режимом immersive fullscreen.

Ожидаемое поведение:

1. Пользователь открывает приложение.
2. Приложение скрывает системные панели и показывает дашборд.
3. Пока Activity видима, часы обновляются каждую минуту, а источники данных — по своей политике.
4. Нажатие кнопки питания выключает экран.
5. После включения Android возвращает пользователя в открытую Activity.
6. В `onResume` приложение немедленно проверяет и обновляет данные.

Настройка `Keep screen on` реализуется через `FLAG_KEEP_SCREEN_ON`. Она должна быть опциональной, потому что e-ink не расходует энергию на удержание изображения, но Android, Wi-Fi, подсветка и другие компоненты продолжают расходовать заряд, пока устройство бодрствует.

### Почему не системная заставка

`DreamService` не является полноценной заменой экрана блокировки и обычно запускается только при зарядке или док-режиме. Его поддержка зависит от прошивки Meebook, а интерактивность и обработка кнопки питания менее предсказуемы.

Live wallpaper тоже не подходит: он находится за системным интерфейсом и неудобен для завершения задач.

### Возможное расширение

После стабилизации основной версии можно добавить опциональный launcher mode. Тогда приложение сможет быть домашним экраном устройства. На первом этапе это не нужно, чтобы не мешать использованию читалки для книг.

## 5. Результат анализа Tesserae

Исследованный проект:

- репозиторий: <https://github.com/dmellok/tesserae>;
- версия на момент анализа: `v0.130.0`;
- лицензия: AGPL-3.0-or-later;
- основной стек: Python 3.11, Flask, Playwright/Chromium, Pillow, JavaScript;
- модель: self-hosted сервер рендерит весь экран в изображение и передаёт его e-ink-клиентам через REST или MQTT.

Схема Tesserae:

```text
Календарь / погода / виджеты
              ↓
       Tesserae-сервер
     Python + Chromium
              ↓
  готовая картинка всего экрана
              ↓
 REST или MQTT → e-ink-устройство
```

Полезные идеи Tesserae:

- модульная система информационных блоков;
- раскладка дашборда из независимых элементов;
- отдельные политики обновления;
- Open-Meteo как источник погоды;
- ориентация на e-ink;
- кэширование данных;
- разделение получения данных и отображения;
- периодическая полная перерисовка;
- отображение состояния устройства.

Почему не следует делать fork:

- Tesserae — сервер, а не Android-приложение;
- потребуется постоянно работающий отдельный сервер;
- Meebook/Android-клиента нет;
- встроенный Todo не связан с Todoist;
- календарь подключается через iCal URL;
- основным результатом является картинка, а не интерактивный UI;
- завершение задач плохо соответствует модели «тонкого клиента»;
- fork унаследует большой объём нерелевантного Python/Chromium-кода;
- AGPL создаёт дополнительные лицензионные обязательства при распространении производной версии.

Решение: создать отдельный Android-проект и использовать Tesserae только как источник идей.

## 6. Выбранный технологический стек

- Kotlin;
- Android SDK;
- одна Activity;
- Jetpack Compose для интерфейса;
- Kotlin Coroutines и StateFlow;
- Room для локального кэша и очереди операций;
- DataStore для настроек;
- Retrofit и OkHttp для сетевых API;
- Android Calendar Provider для календаря;
- Android Keystore для Todoist token;
- JUnit и AndroidX Test;
- screenshot-тесты для основных раскладок.

Рекомендуемые параметры:

- `minSdk = 30` — Android 11;
- `targetSdk` — актуальная стабильная версия на момент создания проекта;
- Java/Kotlin toolchain — согласно выбранной стабильной версии Android Gradle Plugin;
- поддерживать 32-bit Android, пока ADB-проверка не подтвердит ABI устройства.

Compose допустим для e-ink при следующих ограничениях:

- глобально отключить анимации;
- не использовать shimmer;
- не использовать ripple;
- не использовать плавную прокрутку;
- избегать постоянно меняющихся progress indicators;
- обновлять только изменившиеся состояния;
- не перерисовывать весь экран каждую секунду.

## 7. Архитектура

```text
                    Dashboard UI
                         │
            Dashboard State Coordinator
                         │
        ┌────────────────┼────────────────┐
        │                │                │
 Calendar Module    Todoist Module    Weather Module
        │                │                │
CalendarContract    Todoist API       Open-Meteo
        │                │                │
        └────────────── Room ─────────────┘
                         │
              Последнее успешное состояние
```

Предлагаемая структура модулей:

```text
app/
  core/
    database/
    network/
    settings/
    security/
    eink/
    time/
  dashboard/
    model/
    ui/
    layout/
    refresh/
  modules/
    clock/
    battery/
    calendar/
    todoist/
    weather/
  settings/
  diagnostics/
```

Базовый контракт информационного блока:

```kotlin
interface DashboardModule {
    val id: String
    val refreshPolicy: RefreshPolicy

    suspend fun refresh(reason: RefreshReason)
    fun observe(): Flow<ModuleState>
}
```

Не нужно делать систему динамически загружаемых APK-плагинов. Достаточно внутреннего registry:

```kotlin
class DashboardModuleRegistry(
    val modules: List<DashboardModule>
)
```

Настройки каждого блока и его положение хранятся отдельно от реализации. Это позволит позднее добавить RSS, валюты, привычки, заметки или Home Assistant.

## 8. Источники данных

### 8.1 Google Calendar

Использовать системный Android Calendar Provider через `CalendarContract`, а не Google Calendar REST API.

Преимущества:

- используется Google-аккаунт, уже добавленный на Meebook;
- не нужен Google Cloud Project;
- не нужен отдельный OAuth flow;
- доступны несколько календарей;
- названия и цвета календарей уже находятся на устройстве;
- повторяющиеся события разворачиваются через `CalendarContract.Instances`;
- локально синхронизированные события доступны офлайн.

Разрешение:

```xml
<uses-permission android:name="android.permission.READ_CALENDAR" />
```

Запрашивать `WRITE_CALENDAR` не нужно.

Нужно реализовать:

- список видимых календарей;
- включение и выключение отдельных календарей;
- чтение экземпляров событий для выбранного диапазона;
- all-day events;
- повторяющиеся события;
- сортировку по времени;
- группировку по дню;
- корректную обработку часового пояса `Asia/Tashkent`;
- режимы «Сегодня», «Сегодня + завтра», «Неделя».

В grayscale нельзя полагаться только на цвет. Каждый календарь должен иметь комбинацию:

- оттенка;
- формы маркера;
- при необходимости штриховки.

### 8.2 Todoist

Для персональной версии использовать персональный API token.

Настройка:

- пользователь вставляет token один раз;
- приложение проверяет token тестовым запросом;
- token хранится зашифрованно с Android Keystore;
- token нельзя писать в логи, Room или crash reports.

Представления:

- «Сегодня»: просроченные задачи и задачи на сегодня;
- «Предстоящие»: задачи на ближайшие 7 дней;
- группировка по датам;
- приоритет;
- проект;
- labels;
- подзадачи;
- срок и время.

Завершение задачи:

1. Пользователь нажимает checkbox.
2. UI немедленно показывает задачу выполненной.
3. Локально создаётся pending operation.
4. Выполняется запрос Todoist.
5. При успехе операция удаляется.
6. При сетевой ошибке операция остаётся в очереди.
7. При следующем обновлении выполняется повторная отправка.
8. При окончательной API-ошибке UI возвращает задачу и показывает понятное сообщение.

Нужно отдельно протестировать повторяющиеся задачи: после завершения Todoist переносит их на следующую дату.

Если приложение станет публичным, персональный token следует заменить на OAuth.

### 8.3 Погода

Использовать Open-Meteo.

Место по умолчанию:

- Ташкент;
- примерные координаты хранятся как предустановленное место;
- точные координаты пользователь может заменить в настройках.

Опциональная геолокация:

- запрос разрешения только после явного выбора режима;
- использовать последнее известное положение;
- не держать GPS постоянно включённым;
- после определения координат сохранить их и использовать как фиксированное место.

Отображать:

- текущую температуру;
- ощущаемую температуру;
- погодное состояние;
- минимум и максимум на день;
- вероятность и количество осадков;
- ветер;
- прогноз на 7 дней.

Кэшировать последний успешный ответ в Room.

### 8.4 Часы и заряд

Часы:

- системное время;
- обновление на границе каждой минуты;
- обновление после `onResume`;
- корректная обработка смены даты и часового пояса.

Заряд:

- `BatteryManager`;
- BroadcastReceiver для изменения уровня заряда;
- процент;
- состояние зарядки;
- при необходимости индикатор низкого заряда.

## 9. Политики обновления

Каждую минуту не следует запрашивать все внешние API.

| Источник | Рекомендуемая частота |
|---|---:|
| Часы | каждую минуту |
| Календарь | локальный запрос каждую минуту |
| Todoist | каждые 2–5 минут и вручную |
| Погода | каждые 15–30 минут |
| Заряд | по системному событию |
| Полная e-ink перерисовка | настраиваемо, например каждые 30 минут |

Общие правила:

- scheduler работает только пока Activity находится в foreground;
- при `onPause` сетевые циклы останавливаются;
- при `onResume` выполняется немедленная проверка;
- ручное обновление доступно отдельной кнопкой;
- отображается время последнего успешного обновления;
- при ошибке сохраняются старые данные с отметкой об их возрасте.

WorkManager для минутного обновления не использовать. Он предназначен для фоновой работы и не даёт точного интервала в одну минуту.

## 10. E-ink-оптимизация

Android не предоставляет универсального публичного API для управления e-ink. Meebook может иметь собственные системные сервисы, скрытые классы, broadcast-команды или только пользовательские настройки оптимизации для отдельных приложений.

### Гарантированный базовый режим

- статичная геометрия;
- высокая контрастность;
- ограниченная палитра из 4–8 оттенков серого;
- крупный текст;
- минимальное число тонких линий;
- отсутствие анимаций;
- отсутствие прозрачных moving overlays;
- обновление только изменившегося composable;
- дискретное переключение представлений;
- избегать длинного плавного скролла;
- полный redraw после смены ориентации;
- полный redraw после возвращения из сна;
- периодический полный redraw для очистки ghosting.

### Исследование Meebook API

Через ADB необходимо:

- получить список установленных системных пакетов;
- найти пакеты и сервисы с именами `eink`, `epd`, `boyue`, `likebook`, `meebook`;
- посмотреть доступные Activity, Service и BroadcastReceiver;
- изучить системные свойства;
- посмотреть logcat при ручном переключении Normal/Regal/A2;
- проверить наличие vendor JAR;
- проверить, можно ли вызвать полный refresh без root;
- проверить app-specific optimization в системных настройках.

Если официальный или стабильный неофициальный API найден:

- изолировать его в `core/eink`;
- предоставить интерфейс `EInkController`;
- иметь no-op fallback для обычного Android;
- не допускать падения приложения при отсутствии vendor API.

Пример интерфейса:

```kotlin
interface EInkController {
    fun setMode(mode: EInkMode)
    fun requestPartialRefresh()
    fun requestFullRefresh()
}
```

## 13. План реализации

### Этап 0. Обследование устройства

Оценка: 0,5–1 рабочий день.

Задачи:

- включить Developer options;
- включить USB debugging;
- подключиться через ADB;
- получить точную модель;
- определить разрешение, DPI и ABI;
- проверить 32/64-битность;
- определить e-ink системные компоненты;
- проверить поведение Activity после кнопки питания;
- проверить портретную и альбомную ориентации;
- снять базовый расход батареи;
- проверить установку debug APK.

Критерий готовности:

- сохранён технический отчёт по устройству;
- выбран безопасный способ управления e-ink;
- подтверждены параметры сборки APK.

### Этап 1. Каркас приложения

Оценка: 1–2 рабочих дня.

Задачи:

- создать Android-проект;
- настроить Kotlin и Compose;
- добавить Room, DataStore, Retrofit/OkHttp;
- создать Dashboard Activity;
- реализовать immersive fullscreen;
- реализовать portrait/landscape;
- создать module registry;
- добавить минутный ticker;
- отключить анимации;
- создать базовые темы grayscale;
- добавить экран настроек и диагностики.

Критерий готовности:

## 14. Общая оценка

Ожидаемая длительность:

- первый работающий сквозной вариант: 4–6 рабочих дней;
- хорошо отполированная персональная версия: 10–16 рабочих дней.

Наибольшая неопределённость — закрытые e-ink API Meebook. Основные интеграции Calendar, Todoist и Open-Meteo стандартны и не требуют отдельного сервера.

## 15. Риски

### Закрытый Meebook e-ink API

Риск: программный full refresh может быть недоступен.

Снижение риска:

- работать через стандартный Android UI;
- использовать системную app optimization Meebook;
- ограничить изменения UI;
- оставить vendor adapter опциональным.

### Прошивка может быть 32-bit

Риск: некоторые нативные зависимости не установятся.

Снижение риска:

- не добавлять ненужные native libraries;
- проверить ABI до выбора зависимостей;
- использовать преимущественно pure Java/Kotlin библиотеки.

### Чрезмерный расход батареи

Риск: постоянно включённый Android и Wi-Fi расходуют батарею, несмотря на e-ink.

Снижение риска:

- keep-screen-on только как опция;
- разные интервалы API;
- останавливать обновления в background;
- использовать кэш;
- измерить фактический расход.

### Ghosting

Риск: минутные изменения часов накапливают остаточное изображение.

Снижение риска:

- не менять секунды;
- минимизировать изменяемую область;
- периодический full refresh;
- тестировать несколько режимов панели.

### Todoist API

Риск: изменение версии API или ограничения запросов.

Снижение риска:

- изолировать API client;
- использовать официальный текущий API;
- хранить локальный кэш;
- иметь явную обработку 401, 403, 429 и 5xx.

### Calendar sync

Риск: Calendar Provider показывает только данные, которые системный аккаунт успел синхронизировать.

Снижение риска:

- отображать время последнего чтения;
- добавить диагностику доступных календарей;
- документировать необходимость включённой синхронизации Google Calendar.

## 17. Когда может понадобиться Cloudflare

Cloudflare не нужен для персональной первой версии.

Он может понадобиться, если:

- приложение станет публичным;
- Todoist personal token заменяется на OAuth;
- появляются серверные секреты;
- нужна синхронизация конфигурации между устройствами;
- несколько пользователей используют один backend;
- появляется webhook/event-driven обновление.

Возможный стек для будущего:

- Cloudflare Workers;
- D1 или KV;
- OAuth callback;
- encrypted token storage;
- минимальный API без хранения календарных данных.

## 19. Первый следующий шаг

Начать с этапа 0, не с написания всего UI.

Последовательность первого рабочего сеанса:

1. Подтвердить точную модель устройства.
2. Включить Developer options и USB debugging.
3. Установить Android Platform Tools.
4. Выполнить ADB-аудит устройства.
5. Сохранить результаты в отдельный `DEVICE_AUDIT.md`.
6. После подтверждения ABI и e-ink-возможностей создать Android-проект.

Пример минимального набора диагностических команд:

```bash
adb devices
adb shell getprop ro.product.manufacturer
adb shell getprop ro.product.model
adb shell getprop ro.product.device
adb shell getprop ro.build.version.release
adb shell getprop ro.build.version.sdk
adb shell getprop ro.product.cpu.abilist
adb shell wm size
adb shell wm density
adb shell pm list packages
```

Необходимо также записать `logcat` во время ручной смены режима обновления e-ink, чтобы найти vendor-команды.
